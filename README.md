# 幻想宴会ドラフト

東方Project 二次創作のカードドラフトゲーム（スシGO 風メカニズム × 幻想郷の宴会テーマ）。
Web ゲーム（HTML/JS + `ws`）として動作する。

> 東方Project二次創作ガイドラインに従い、非商用の個人ゲームとして制作。

## 遊び方

```bash
npm start
# → http://localhost:3010 を開く
```

- 最初の画面で「ひとりで遊ぶ（AI3人）」か「みんなで遊ぶ（ルーム）」を選ぶ
- ひとりモードでも異変を選べる（おまかせ / 紅霧 / 春雪 / 永夜）
- 3 ラウンド・各ラウンドで手札から 1 枚選んで隣にパス（スシGO 流ドラフト）
- 同点は**デザートの合計枚数が多い方**が上位。それも同じなら同率1位
- ゲーム開始時に**異変が 1 つ抽選**され、デッキの顔つきが全く変わる

### 対戦（2〜5人）

- 「ルームを作る」→ 表示された 4 文字コードを相手に伝える
- 相手は「コード」を入れて「参加する」
- **ルームマスター**が「異変」と「取得時間（30秒 / 60秒 / 無制限）」を設定できる（開始後は変更不可）
- ホストが「ゲーム開始」を押すと開始
- 手札は各自の画面にだけ表示（山札・他人の手札・未公開のピックはサーバーが隠す）
- 取得時間を過ぎると AI が代行する（残り時間は画面右上に表示）。ラウンド結果バナーは 10 秒で自動的に閉じる
- 切断しても、同じ名前・同じルームで入り直すと元の席に戻る
- 切断したままの席は 1.5 秒後に AI が代行する（ゲームが止まらない）

```bash
npm test
# ルールテスト（72 テスト）を実行
npm run test:ws
# 対戦サーバーのスモークテスト（join/start/ピック/秘匿/再接続）
```

## 異変パックシステム

ゲーム開始時に 3 つの異変から 1 つが抽選される。各異変は独立したカードパック
（10 種・メイン 54 枚＋デザートプール 15 枚）を持ち、駆け引きの「形」が異なる。

| 異変 | 物語 | 駆け引きの形 |
|---|---|---|
| 紅霧異変（紅魔郷） | 紅の館の夜会 | キャラ間連携（咲夜×美鈴・大妖精×チルノ） |
| 春雪異変（妖々夢） | 白玉楼の桜見宴会 | 軸（春）への 4 方向攻防 |
| 永夜異変（永夜抄） | 永遠亭の月見宴会 | 数量の管理とジレンマ（偶奇・豆腐・乱入者） |

- デザート枠（チルノ / リリーホワイト / 妹紅）はデザートプールから
  ラウンドごとに 5/3/2 枚山札に混入し、ゲーム末（またはラウンド末）に判定される
- ラウンド終了時に取得カードはデザート以外すべて山札に戻る（スシGOパーティー準拠）
- 永夜異変はゲーム開始時に乱入者（霊夢/魔理沙）がランダムで 1 種のみデッキに加わる

詳細は `DESIGN.md` を参照。

## 開発

```
touhou-draft/
├── index.html      ロビー + ゲーム画面 DOM
├── style.css       和風ダークテーマ（紅/藍）
├── data.js         異変パック定義（INCIDENTS: 各異変のカード 10 種と枚数）
├── engine.js       ヘッドレスエンジン（newGame / dispatch / scorePlayer）
├── ai.js           AI プレイヤー（ヒューリスティック選択）
├── game.js         UI 描画・入力（ホットシート / 対戦クライアント）
├── room.js         対戦ルーム管理・席ごとのビュー（サーバー権威）
├── net.js          対戦クライアント（ws・再接続）
├── server.js       静的配信 + WebSocket サーバー
└── tools/
    ├── rules-test.js  ルールテスト（node 直実行）
    ├── ws-test.js     対戦サーバーのスモークテスト
    ├── sim.js         AI vs AI バランスシミュレーション
    ├── attrib.js      得点源の分解（どのカードが点を出しているか）
    └── ai-check.js    AI の「標準らしさ」検証（同型対戦・摂動耐性・異種混合）
```

- エンジンはヘッドレス（DOM 非依存）。ブラウザ・Node・将来の権威サーバーで同一ルール
- `dispatch(state, action)` が全変更の単一エントリポイント（`{ok}` / `{ok:false, error}`）
- Cascadia プロジェクト（`../New Game`）の設計方針を踏襲

### バランス確認

```
npm test                        # ルールテスト
npm run sim                     # 全異変 × 300 ゲーム（AI 4 人）
npm run sim -- --games 1000     # 試行回数を増やす
npm run sim -- --incident spring --top 20
npm run sim -- --csv > sim.csv  # スプレッドシート用
npm run sim -- --out .tmp/sim-report.txt  # UTF-8 ファイルにも書き出す（Windows の文字化け対策）
npm run sim -- --ablate y_kaguya          # 点数を 1 下げたときの影響（感度分析）
```

指標は 2 つあり、用途が違う。

**卓平均差（相対指標）** — そのカードを取った人が同じラウンドで他プレイヤーより何点上だったかの平均。
+ が大きい = 持っていると勝ちやすい、− が大きい = 持っていても勝てない。
ただし全員が同じ頻度で強いカードを引くため **カードの絶対的な強さは相殺される**。
実際、点数を動かしても単調に動かない（4 点でも 2 点でも同じ値になったりする）。
条件付きカード・デザートは構造的に下振れするので、これ単独で弱いと断定しないこと。

**感度分析 `--ablate`（絶対指標）** — 指定カードの点数を `--step` 点（既定 −1）動かして再実行し、
卓全体の平均合計点が何点動くかを見る。点経済への寄与を素直に測れるので、
ナーフ・バフの効き具合はこちらで確認する。`--seed` で乱数を固定できる。

**得点源の分解** — `npm run attrib` で、カード 1 種類の得点ロジックを 0 にして再実行し、
パック平均が何点下がるか（＝そのカード全枚数の寄与）を一覧にする。
`1枚あたり` 列は点が枚数に比例する instant だけ算出する。マキ・手巻き・共闘・収集などは
枚数や順位で段階的に変わるため、割り算した値に意味がない。
「1 枚が強い」のか「枚数が多いから合計が大きい」のかを切り分けるのに使う。

```
npm run attrib
npm run attrib -- --incident eternal --games 1500 --out .tmp/attrib.txt
```

**所持枚数分析 `--by-card`** — 指定カードを「ラウンド内に何枚持ったか」ごとに、ラウンド点の卓平均との差と
勝率を出す。取るほど勝てるカード（dominant）と、取るほど損になるカード（sucker）を切り分けられる。

```
npm run sim -- --games 1500 --by-card y_tewi
npm run sim -- --games 1500 --by-card y_riggle
```

### AI の検証

```
npm run ai-check
```

AI の評価関数が「標準的」と言えるかを 3 つの観点で確認する（4200 ゲーム、標準誤差 約0.7%）。

1. **同型対戦** — 同じ AI 4 人で 25% 前後（偏りがない）
2. **摂動耐性** — 評価を ±10% ずらした相手に負けない（簡単に搾れない）
3. **異種混合** — 癖のある相手 3 人（即時好き・セット好き・順位＋デザート好き）を相手に 18% 以上

カード評価を変えたら、ここが合格するか確認する。
